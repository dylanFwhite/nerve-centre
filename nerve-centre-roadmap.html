nerve-centre: roadmap and architecture

A Raspberry Pi 5 "nerve centre" that collects data from home projects. It starts with a colour e-ink commute dashboard (TfL and weather) and later grows into greenhouse automation.

Key decisions

Hub

Raspberry Pi 5 (4 GB), booting from an NVMe SSD, running Raspberry Pi OS Lite (64-bit)

Language

Rust wherever possible. The display client is Python, to use Pimoroni's driver

Event bus

Eclipse Mosquitto (MQTT)

Services

One binary per service, each its own systemd unit, restarted independently

Storage

SQLite (WAL mode), written only by the data service

Display

Pimoroni Inky Impression 7.3" (6-colour Spectra 6 e-ink), image rendered on the hub

First project

Commute dashboard: Tube and Elizabeth line status (now and 7 days ahead) and London weather from Open-Meteo

System architecture

Everything except the two displays runs on the Pi 5. Services talk only through the event bus, so the dashboard keeps working even if storage has a problem.

Pollers

Fetch data from TfL and the weather API on a schedule and publish it as events. Only these talk to the outside world.

Node agent

Runs on every Linux node. Every 60 s it publishes the node's CPU, memory, temperature, throttling and disk use, plus memory and CPU for each systemd service it's configured to watch, read from systemd's own accounting.

Mosquitto

The event bus. Retained messages hold the latest value on each topic, so new subscribers get current state straight away. Every payload carries an event ID and publisher timestamp.

Data service

Subscribes to everything at QoS 1 with a persistent session, so the broker queues events while it restarts. Skips event IDs it has already stored, which covers retained resends and duplicate deliveries. It's the only writer to the SQLite database.

Renderer + HTTP

Keeps the latest state in memory and tracks when it last heard from each source. It redraws the PNG when the status changes or when a source goes stale or recovers, then serves it. It doesn't depend on the database.

Display Pi

Pi with the Inky Impression 7.3" attached. A small Python script using Pimoroni's driver fetches the PNG and refreshes the panel only when the image has changed. This is the only part of the system not written in Rust.

Greenhouse nodes Future

Sensor and watering nodes (hardware to be chosen) publishing to the same bus. They keep a local fallback schedule if the hub is down.

Analytics

Opens the SQLite file read-only, so it never blocks the data service. Its first use is the desk display's 24-hour sparklines. DuckDB can attach the same file for heavier analysis without running a second database.

Desk display

A small LCD or similar on the desk. It subscribes to node/ and service/ topics for live health of every node and service, and draws 24-hour sparklines from analytics queries.

Event log schema

One table of raw events. SQLite's JSON functions query inside payloads, and views or generated columns are added only when a query needs them.

CREATE TABLE events (
  id          TEXT PRIMARY KEY,   -- event ID from the publisher (dedupe)
  topic       TEXT NOT NULL,
  ts          INTEGER NOT NULL,   -- publisher timestamp, unix ms
  received_at INTEGER NOT NULL,
  payload     TEXT NOT NULL       -- JSON
);
CREATE INDEX events_topic_ts ON events(topic, ts);

Message design

Every topic starts with a root from config: home/ on the Pi, dev/ on the dev machine. Each data source publishes one message holding its whole current state.

TopicContentsPublished
{root}/tfl/statusCurrent status of every Tube line and the Elizabeth lineOn change · polled every 60 s
{root}/tfl/plannedPlanned disruptions for the next 7 daysOn change · polled every 30 min
{root}/weather/forecastLondon: now and the rest of todayOn change · polled every 15 min
{root}/node/{name}/statsNode resources: CPU, memory, temperature, throttling, disk, and CPU and memory per serviceEvery 60 s, not on change
{root}/service/{name}Service health: online or offline, and the time of the last successful fetchEvery poll · offline set by Last Will

All topics are retained. The data service logs every data message, including every node/ sample, but only the online and offline changes from service/ topics, not every heartbeat.

Publishing on change

Each poller keeps the last payload it published in memory. After every fetch it converts the response into our payload type and compares it with that copy. It publishes only if they differ. Envelope fields are not compared. After a restart the memory is empty, so the first fetch is always published. Node stats are the exception: the values change with every sample, so they are published on a fixed interval.

Staleness

Data topics stay quiet when nothing changes, so the renderer reads freshness from service/{name}. A panel is marked stale when its poller's last successful fetch is older than 3× its poll interval. Node stats carry their own interval_s, so a node is stale after 3× that with no config needed by the reader.

Envelope

Every data message is JSON, wrapped in the same envelope defined in nerve-core. JSON is chosen for observability: it reads directly in MQTT Explorer and SQLite can query inside it.

{
  "id": "0199d4a2-7c3e-7b1a-9f00-3c5e8a1b2d4f",  // UUID v7: unique and sorts by time, used for dedupe
  "ts": "2026-10-12T19:42:05.123Z",              // published at, UTC (stored as unix ms)
  "source": "poller-tfl",                        // publishing service
  "v": 1,                                        // version of the data format
  "data": { ... }
}

Payloads

tfl/status, from TfL's /Line/{ids}/Status, where {ids} is the comma-separated list of lines in config ([tfl] lines). level is our own rating (good, minor, severe, closed, unknown) mapped from TfL's codes, so the renderer never needs to know them.

{ "lines": [
  { "id": "victoria", "name": "Victoria", "mode": "tube", "level": "good",
    "statuses": [ { "code": 10, "description": "Good Service", "reason": null } ] }
] }

tfl/planned, from /Line/{ids}/Status/{from}/to/{to}. The date range only works with line IDs, not with /Line/Mode/…. The response mixes categories, and only PlannedWork is kept: RealTime delays are already in tfl/status, and Information is the normal timetable (e.g. Waterloo & City not running at weekends). One disruption can cover several separate periods.

{ "from": "2026-10-13", "to": "2026-10-19",
  "disruptions": [
    { "line_id": "district", "level": "severe", "description": "Part Closure",
      "detail": "No service between Turnham Green and Ealing Broadway…",
      "periods": [ { "starts": "2026-10-17T03:30:00Z", "ends": "2026-10-19T00:29:00Z" } ] } ] }

weather/forecast, from Open-Meteo (free, no API key). condition is our own short list (clear, partly cloudy, cloudy, fog, drizzle, rain, heavy rain, snow, thunderstorm) mapped from Open-Meteo's weather codes (see Mappings below). hours holds each hour after the current one until midnight, local time. Times are requested as Unix timestamps and converted to Europe/London by the poller, so clock-change days come out right. Wind is in mph. Sunrise and sunset let the renderer draw night icons after dark.

{ "location": "London",
  "now":   { "temp_c": 14.2, "feels_like_c": 12.8, "condition": "drizzle", "precip_mm": 0.3,
             "wind_mph": 11.0, "gust_mph": 24.0 },
  "today": { "high_c": 16.0, "low_c": 9.5, "rain_chance_max": 70,
             "sunrise": "2026-10-12T07:16:00+01:00", "sunset": "2026-10-12T18:13:00+01:00" },
  "hours": [ { "time": "2026-10-12T21:00:00+01:00", "temp_c": 13.1, "condition": "cloudy", "rain_chance": 20 } ] }

node/{name}/stats, from node-agent. CPU is averaged over the interval. Per-service figures come from systemd's MemoryCurrent and the change in CPUUsageNSec between samples. throttled is true if the Pi is throttling or under-voltage.

{ "interval_s": 60,
  "cpu_pct": 12.4, "load_1m": 0.31,
  "mem_used_mb": 812, "mem_total_mb": 4096,
  "temp_c": 51.2, "throttled": false,
  "disk_used_pct": 8.1, "uptime_s": 183000,
  "services": [ { "name": "mosquitto", "mem_mb": 4.3, "cpu_pct": 0.1 },
                { "name": "poller-tfl", "mem_mb": 6.1, "cpu_pct": 0.2 } ] }

Development and deployment

There's no local copy of the system. Mosquitto runs only on the Pi 5, and whichever service you're working on runs on the dev machine and connects to it over the home network.

Dev environment

Native Windows, using VS Code or RustRover with the Windows Rust toolchain. Code is written to run on both Windows and Linux; Linux-only parts (systemd units, the Pi's builds) are handled at deploy time.

Testing

Run services locally against the Pi's Mosquitto. A dev/ topic prefix keeps test data out of the live dashboard. Each client needs a unique ID. Most tests use saved API responses and don't need the broker at all.

Build

Cross-compile for ARM 64-bit Linux with cross, which builds inside a Linux container using Docker Desktop. SQLite is bundled through rusqlite and compiles in seconds. Fall back to building on the Pi 5 if needed.

Deploy

Each service runs as a systemd unit. A justfile builds, copies over SSH and restarts. The same binary runs everywhere, with TOML config for each environment. Secrets stay on the Pi.

Project structure

One repository holding a Cargo workspace. Every service shares nerve-core, so changing a message type is checked across all of them at compile time.

nerve-centre/
├── Cargo.toml            # workspace: members and shared dependency versions
├── crates/
│   ├── nerve-core/       # shared message envelope, topics, config, MQTT helpers
│   ├── poller-tfl/
│   ├── poller-weather/
│   ├── data-service/
│   ├── node-agent/       # node and per-service resource stats
│   └── renderer/         # includes the HTTP endpoint
├── display-client/       # Python, runs on the display Pi (outside the Cargo workspace)
├── deploy/
│   ├── systemd/          # one .service file per service
│   └── mosquitto/        # broker config
├── config/               # dev.toml, prod.toml (no secrets)
└── justfile              # build, deploy and log commands

Any microcontroller firmware for the greenhouse will probably live in a separate workspace, because it builds very differently.

Principles

  • Grow the hub only when something needs it. No rules engine, analytics or extra services until a project calls for them.
  • Services connect through the bus. Adding a data source shouldn't require changes to existing services.
  • Show when data is stale. Every panel shows when its status last changed. If a source goes quiet for too long, the renderer marks that panel stale, so outdated "Good service" is never shown as current.
  • Log every event exactly once. Payloads carry an event ID, and the data service uses a persistent QoS 1 session and drops IDs it has already stored.
  • Keep the raw history. Store every event so it can be reprocessed later.
  • Hardware fails safe. The watering system keeps working without the hub and can't overflow.
