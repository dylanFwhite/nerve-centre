nerve-centre: roadmap and architecture

A Raspberry Pi 5 "nerve centre" that collects data from home projects. It starts with a colour e-ink commute dashboard (TfL and weather) and later grows into greenhouse automation.

Key decisions

Hub

Raspberry Pi 5 (4 GB), booting from an NVMe SSD, running Raspberry Pi OS Lite (64-bit)

Language

Rust wherever possible. The display client is Python, to use Pimoroni's driver

Event bus

Eclipse Mosquitto (MQTT)

Storage

SQLite (WAL mode), written only by the data service

Display

Pimoroni Inky Impression 7.3" (6-colour Spectra 6 e-ink), image rendered on the hub

First project

Commute dashboard: TfL line status and weather

Roadmap

  1. 0

    Set up the hub

    Start here
    • Hardware ordered: Active Cooler, M.2 HAT+ with a 256 GB 2242 NVMe SSD, and the Inky Impression 7.3" display. Check you have the official 27 W power supply
    • Flash Raspberry Pi OS Lite (64-bit) to the SSD with Raspberry Pi Imager, setting the hostname, user and SSH key
    • Fit the HAT, SSD and cooler, then update the bootloader and set it to boot from NVMe
    • Reserve the Pi's IP address in the router and turn on automatic security updates
  2. 1

    Dashboard software

    Software only
    • Pollers for TfL (current and planned disruptions) and the weather forecast
    • Mosquitto on the hub, plus a data service that logs every event to SQLite
    • Renderer that draws the dashboard as a PNG and serves it over HTTP

    Useful straight away: check the dashboard in a browser before leaving.

  3. 2

    E-ink display live

    Needs the display
    • A small Python client on the display Pi fetches the PNG and, using Pimoroni's inky library, refreshes the panel only when it has changed
    • Prototype on the spare Pi 4, move to a small board later
    • Frame and mount it by the door

    The dashboard is on the wall.

  4. 3

    Greenhouse on the bench

    Needs sensors
    • Soil moisture and climate sensors on ESP32 nodes, publishing to the hub
    • Watering controller with a float-switch cutoff and a local fallback schedule
    • Add a greenhouse panel to the dashboard

    Built and tested indoors before it goes in the greenhouse.

  5. 4

    Greenhouse install

    Growing season
    • Move the tested setup into the greenhouse in time for the growing season

    Watering runs on soil moisture instead of a fixed timer.

  6. +

    Later, optional

    Optional
    • Notifications and a commute status light by the door
    • Analytics through the data service, such as commute reliability over time
    • More data sources as new projects come along

System architecture

Everything except the display runs on the Pi 5. Services talk only through the event bus, so the dashboard keeps working even if storage has a problem.

Pollers

Fetch data from TfL and the weather API on a schedule and publish it as events. Only these talk to the outside world.

Mosquitto

The event bus. Retained messages hold the latest value on each topic, so new subscribers get current state straight away. Every payload carries an event ID and publisher timestamp.

Data service

Subscribes to everything at QoS 1 with a persistent session, so the broker queues events while it restarts. Skips event IDs it has already stored, which covers retained resends and duplicate deliveries. It's the only writer to the SQLite database.

Renderer + HTTP

Keeps the latest state in memory and tracks when it last heard from each source. It redraws the PNG when the status changes or when a source goes stale or recovers, then serves it. It doesn't depend on the database.

Display Pi

Pi with the Inky Impression 7.3" attached. A small Python script using Pimoroni's driver fetches the PNG and refreshes the panel only when the image has changed. This is the only part of the system not written in Rust.

Greenhouse nodes Future

ESP32 sensor and watering nodes publishing to the same bus. They keep a local fallback schedule if the hub is down.

Analytics Future

Opens the SQLite file read-only, so it never blocks the data service. DuckDB can attach the same file for heavier analysis without running a second database.

Event log schema

One table of raw events. SQLite's JSON functions query inside payloads, and views or generated columns are added only when a query needs them.

CREATE TABLE events (
  id          TEXT PRIMARY KEY,   -- event ID from the publisher (dedupe)
  topic       TEXT NOT NULL,
  ts          INTEGER NOT NULL,   -- publisher timestamp, unix ms
  received_at INTEGER NOT NULL,
  payload     TEXT NOT NULL       -- JSON
);
CREATE INDEX events_topic_ts ON events(topic, ts);

Development and deployment

There's no local copy of the system. Mosquitto runs only on the Pi 5, and whichever service you're working on runs on the dev machine and connects to it over the home network.

Dev environment

Native Windows, using VS Code or RustRover with the Windows Rust toolchain. Code is written to run on both Windows and Linux; Linux-only parts (systemd units, the Pi's builds) are handled at deploy time.

Testing

Run services locally against the Pi's Mosquitto. A dev/ topic prefix keeps test data out of the live dashboard. Each client needs a unique ID. Most tests use saved API responses and don't need the broker at all.

Build

Cross-compile for ARM 64-bit Linux with cross, which builds inside a Linux container using Docker Desktop. SQLite is bundled through rusqlite and compiles in seconds. Fall back to building on the Pi 5 if needed.

Deploy

Each service runs as a systemd unit. A justfile builds, copies over SSH and restarts. The same binary runs everywhere, with TOML config for each environment. Secrets stay on the Pi.

Project structure

One repository holding a Cargo workspace. Every service shares nerve-core, so changing a message type is checked across all of them at compile time.

nerve-centre/
├── Cargo.toml            # workspace: members and shared dependency versions
├── crates/
│   ├── nerve-core/       # shared message envelope, topics, config, MQTT helpers
│   ├── poller-tfl/
│   ├── poller-weather/
│   ├── data-service/
│   └── renderer/         # includes the HTTP endpoint
├── display-client/       # Python, runs on the display Pi (outside the Cargo workspace)
├── deploy/
│   ├── systemd/          # one .service file per service
│   └── mosquitto/        # broker config
├── config/               # dev.toml, prod.toml (no secrets)
└── justfile              # build, deploy and log commands

The ESP32 greenhouse firmware will probably live in a separate workspace, because it builds very differently.

Principles

  • Grow the hub only when something needs it. No rules engine, analytics or extra services until a project calls for them.
  • Services connect through the bus. Adding a data source shouldn't require changes to existing services.
  • Show when data is stale. Every panel shows when its status last changed. If a source goes quiet for too long, the renderer marks that panel stale, so outdated "Good service" is never shown as current.
  • Log every event exactly once. Payloads carry an event ID, and the data service uses a persistent QoS 1 session and drops IDs it has already stored.
  • Keep the raw history. Store every event so it can be reprocessed later.
  • Hardware fails safe. The watering system keeps working without the hub and can't overflow.
